# Отчёт об использовании ИИ в академической работе

## Задание

`Загрузите одну из своих академических работ, выполненных с помощью ИИ-инструментов, и приложите отчёт о том, как именно вы использовали ИИ при её подготовке.`
см. CHAT.md

## Образовательная цель

`Чему вы должны были научиться, выполняя это задание?`
В рамках курса Скриптовые языки и управление ОС
Я. Практикума на направлении DevOps есть задание - развернуть terraform на облачном сервере Яндекса. Но зачем Яндекс, если у меня есть локальный сервер на Proxmox? И к нему оказывается тоже есть возможность подключить terraform как провайдер инфраструктуры.

В целом сам провайдер я нашел сам, но были проблемы из-за санкций и напрямую из репозитория плагинов terraform он не подтягивался. Тут на помощь ИИ и пришел.

Из практической части я освоил:
- Архитектуру установки провайдеров Terraform: различие между `dev_overrides`, `filesystem_mirror` и `plugin_cache`, а также корректную иерархию каталогов, повторяющую реестр (`registry.terraform.io/<namespace>/<name>/<version>/<platform>`).
- Методы аутентификации Proxmox: `api_token` vs `username/password` и влияние прав токена на успех `apply`.
- Отладку по принципу разделения причин (separation of concerns): сетевая проблема vs проблема авторизации vs ошибка конфигурации.
- Интроспекцию схемы провайдера через `terraform providers schema -json` + `jq` для чтения описаний атрибутов.

## Использованные ИИ-инструменты

`Какие инструменты вы выбрали и как обосновываете свой выбор?`
Веб-чат: Qwen 3.7 Plus - [chat.qwen.ai](веб чат) — консультант для диагностики (сессия по `terraform init`).  
Агент: Gigacode (vs code) — использовался для изменений в конфигурационных файлах (сессия по `terraform plan` / `apply`).

## Распределение вклада

`Каков ваш вклад в финальную работу, а каков вклад ИИ?`

Сессия 02 (`terraform init`): ИИ диагностировал проблему — `dev_overrides` предназначен для разработки провайдера из исходников, а не для pre-compiled бинарников — и предложил заменить на `filesystem_mirror` с корректной структурой каталогов. Я выполнял команды, копировал бинарник и запускал `terraform init` / `terraform plan`.

Сессия 01 (`terraform plan` / `apply`): я самостоятельно проверил доступ к зеркалам через `curl -I`, затем проверил Proxmox API двумя способами (API-токен и `username/password`). ИИ интерпретировал результаты: определил, что API-токен возвращает 401, а парольная аутентификация работает — и предложил переключить `provider.tf` на `username/password`. Дальше передал управление агенту (Gigacode), чтобы он внёс изменения в конфиг и запустил `terraform apply`.

Распределение: ИИ — диагностика и подбор решения; я — исполнение, проверка гипотез в терминале и управление агентом.

## Данные и безопасность

`Какие данные вы передавали ИИ-инструментам? Было ли безопасно их передавать?`  
Данные — вывод из терминала, фрагменты конфигурационных файлов (`provider.tf`, `versions.tf`, `.terraformrc`).

Риск: части кредов (API-токен, пароли) содержались в `terraform.tfvars` и попали в контекст чата при отправке файлов. Митигация: Proxmox-сервер локальный (192.168.x.x, только моя ЛВС), креды от непродуктивной машины для практического занятия; в отчёте и в чатах значения заменены на `******`.

## Верификация результата

`Как вы проверяли результаты работы ИИ?`
Верификация шла цепочкой, на каждом этапе:

1. После исправления `.terraformrc` (сессия 02) — `terraform init` успешно скачал провайдер из локального mirror, `terraform plan` вернул "No changes" (без ошибок по схеме).
2. Перед `apply` (сессия 01) — проверил сетевой доступ на стороне Proxmox: `ssh root@192.168.x.x 'curl -I https://cloud.debian.org/images/.../'` — зеркала отвечали OK, значит проблема не в сети.
3. Проверил Proxmox API напрямую: два запроса `curl` с разными методами аутентификации (API-токен и `username/password`) — API-токен возвращал 401, парольная пара работала. Это локалировало причину в правах токена.
4. После смены метода аутентификации — `terraform plan` показал "8 to add", `terraform apply` создал все 8 ресурсов (iso / qcow2 / vztmpl).
5. Проверка итога: `terraform plan` после `apply` — "No changes. Your infrastructure matches the configuration."

Кроме того, для понимания атрибутов ресурса использовал `terraform providers schema -json | jq -r '...'` и сверял с документацией.
